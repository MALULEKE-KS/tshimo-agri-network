0  Executive Summary

Final Submission · 16 October 2026

The problem

Tshimo Agri Supplies, an agricultural supplier in Potchefstroom, needs a head-office network: separated departments, internal DHCP, DNS and file services, and internet access over one ISP link, inside the assigned block 10.23.0.0/16. A branch office may open within 18 months and Change Request CR1 adds eight staff to one department; neither may force a redesign. The assigned challenge is Network Troubleshooting — fault isolation, Advanced.

The solution

One edge router (R1) does router-on-a-stick inter-VLAN routing, DHCP relay and NAT/PAT. One Layer 2 core switch trunks R1 to four access switches, one per department. Four business VLANs, each a uniform /26 (62 usable hosts) whatever the current headcount, plus management/native VLAN 99. All of HQ sits inside 10.23.0.0/23, one summarisable block, and 10.23.128.0/17 is reserved untouched for the branch.

The results

  • The design was built in Cisco Packet Tracer 9.0.1 without changing a single VLAN, subnet or gateway from the Milestone 1 plan: 7 network devices, 40 PCs, 3 servers, 49 links.
  • 12 of 12 functional tests passed: cabling, VLANs, trunks, router interfaces and routes, DHCP via relay, same-VLAN and inter-VLAN pings, DNS and web, NAT, and CR1 capacity.
  • CR1 was absorbed on the live network: Warehouse grew from 12 to 20 PCs by assigning eight more access ports to VLAN 30. No subnet, gateway, trunk or router change was needed.
  • The assigned fault was injected, isolated and fixed. VLAN 30 was removed from one trunk; Warehouse lost its gateway while local switching survived; an Admin control test scoped it; show interfaces trunk isolated it; a one-line fix and repeat tests verified recovery.
  • The branch requirement is met by design: a proposed plan (Section 6.2) needs only a spare router port, one static route and one ACL line at HQ.

2.2  The addressing arithmetic

A /26 leaves 6 host bits: 26 = 64 addresses, minus the network and broadcast addresses = 62 usable hosts. Each business VLAN gets one, whatever its headcount today:

VLANSubnetUsable rangeDevices nowUsed of 62Free
10 ADMIN10.23.0.0/26.1 – .628 PCs13%54
20 SALES10.23.0.64/26.65 – .12612 PCs19%50
30 WAREHOUSE10.23.0.128/26.129 – .19020 PCs (12 + 8 CR1)32%42
40 SERVERS10.23.0.192/26.193 – .2543 servers5%59
99 MGMT-NATIVE10.23.1.16/28.17 – .30gateway + 5 switch SVIs43% of 148

Usable ranges include the R1 gateway address (the first usable address of each subnet); "Free" subtracts the gateway and devices. Why uniform and over-sized? A /27 (30 hosts) would also have covered CR1's 20 Warehouse staff, but would leave only 10 spare, so the next growth step would force a re-address. The four business /26s together use 256 addresses, 0.4% of the /16; the whole HQ footprint, 10.23.0.0/23, is 512 addresses, 0.78%. Over-provisioning costs almost nothing here, and one uniform rule (every department gets a /26) is easier to operate and to explain than four custom sizes. A real limit to note: the DHCP pools lease 50 addresses, so the first ceiling Warehouse would hit is the pool (raisable to 53 from its current start of .138) rather than the subnet.

2.3  Address-space map and summarisation

Why the summary works. 10.23.0.0/24 and 10.23.1.0/24 differ only in the last bit of the third octet, so the first 23 bits are identical and one /23 covers both. Any future router upstream of HQ needs one route, not nine. Why a whole /17 for the branch? The brief gives no branch headcount or structure, so rather than invent one, the plan fixes what is known (HQ) and holds back half the allocation, untouched, until the branch's real requirements exist.

3  Implementation — Switching

Section 3 of 10

3.2  VLANs and trunks

  • VLAN database. SW-CORE holds all five VLANs because every VLAN crosses it. Each access switch creates only the VLAN its ports use, plus VLAN 99.
  • Trunks. Every switch-to-switch and switch-to-router link is a static 802.1Q trunk (switchport mode trunk) with native VLAN 99 and an explicit allowed list of 10,20,30,40,99.
  • Access ports. Each department's port range is a static access port in its VLAN, with PortFast so PCs come up without waiting for spanning tree.
  • Management. Each switch has an SVI on VLAN 99 — SW-CORE .18, SW-ADM .19, SW-SAL .20, SW-WH .21, SW-SRV .22 (all /28) — with default gateway 10.23.1.17.

5  Advanced Fault Isolation

Section 5 of 10 · Assigned challenge

5.1  The scenario

A change on the core switch removes VLAN 30 (Warehouse) from the allowed-VLAN list on the SW-CORE → SW-WH trunk. It is a realistic one-word mistake: typing switchport trunk allowed vlan 10,20,40,99 instead of …10,20,30,40,99, or running remove 30 on the wrong port.

Why it qualifies as Advanced:

  • The physical link stays up. Link lights and Layer 1 checks look healthy, so the fault cannot be seen on the topology.
  • The failure is partial. Warehouse PCs can still reach each other, which can mislead a troubleshooter into blaming the gateway, DHCP or the PCs.
  • The two ends of the trunk disagree: SW-WH still allows VLAN 30 and SW-CORE does not. Checking only one end misses it.
  • It is a one-line mistake with a one-line fix, so finding it depends on method, not on rebuilding anything.

5.2  Method

Work up the OSI model and move up a layer only once the one below is proven good. Use a control test from an unaffected department to scope the fault before touching any device. Treat expected symptoms as hypotheses to check, not conclusions.

5.4  Step 2 — Inject the fault (on SW-CORE, not saved)

5  Fault — Evidence & Root Cause

Section 5 of 10
Root cause. SW-CORE Fa0/3 is the only physical path between SW-WH and the rest of the network. With VLAN 30 removed from that trunk's allowed list, no VLAN 30 frame can cross it. Warehouse PCs can still switch locally, but lose everything that depends on reaching R1. Mode, encapsulation and native VLAN are all correct, so the fault is purely the trunk's VLAN membership.

6.2  Branch office design proposal — not built, not simulated

The brief says only that a branch may open within 18 months, with no headcount or structure. So the branch is delivered as a design that proves the reservation works, not as a build. It is a proposal: the branch's real requirements would be confirmed with the client first, and none of it has been configured or tested in Packet Tracer. The idea: the branch mirrors HQ's layout shifted by +128 in the third octet.

PurposeHQ (built)Branch (proposed)
VLAN 10 / 20 / 30 / 40 blocks10.23.0.0 / .64 / .128 / .192 (/26)10.23.128.0 / .64 / .128 / .192 (/26)
VLAN 99 management / native10.23.1.16/2810.23.129.16/28
Site summary route10.23.0.0/2310.23.128.0/23
Inter-site link (/30)10.23.1.4/30 — R1 .5, branch router .6; inside HQ's existing /23 summary
  • Link. R1's third Gigabit port (Gi0/2) is unused and shut (Figure 5), so it can carry the inter-site link with no new HQ hardware. In production that link would be a site-to-site VPN over the ISP or a leased line, depending on what the client will pay for; in Packet Tracer a direct Ethernet link would stand in for it.
  • Routing. Two static routes are enough for two sites: at HQ, ip route 10.23.128.0 255.255.254.0 10.23.1.6; at the branch, a default route to 10.23.1.5. A routing protocol is not justified at this scale.
  • What changes at HQ: a cable to Gi0/2, that port's configuration, the one static route, and one line added to the NAT ACL (access-list 1 permit 10.23.128.0 0.0.1.255) if the branch is to reach the internet through HQ. What does not change: every HQ VLAN, subnet, gateway, trunk, DHCP pool and switch. The NAT line is a real, small HQ change, and it is stated here rather than hidden.
  • Capacity. 10.23.128.0/17 holds 64 blocks of /23, each as large as HQ's whole footprint, so further sites need no HQ change either.

The full proposal, with a verification plan for when the branch is built, is in docs/11-branch-office-design-proposal.md.

The access-port block from sw-wh.txt had turned three of its trunks (to SW-SAL, SW-WH, SW-SRV) into VLAN 30 access portsRe-applied sw-core.txt in full, confirmed all trunks with show interfaces trunk, saved, then re-injected only the one-line fault and re-ran every symptom testConfirming a device's identity with CDP, and refusing to accept a symptom that did not fit the design
Why the last one matters. The first symptom test did not match the prediction: Admin failed too. Instead of recording it as the result, the mismatch was treated as a second, unknown problem and run down. All symptoms in Section 5 come from the clean rerun. The failed Admin pings from the misconfigured period remain visible higher up in the original capture's scrollback; they belong to that period, not to the assigned fault. An early explanation of those failures as spanning tree reconverging was wrong; the cause was the pasted configuration, and the repository records carry the corrected account.
Practices adopted from these incidents. Open each device's CLI fresh and read the prompt before pasting anything. Never paste a file whose header does not match the device. Verify identity with CDP when a symptom does not fit.

9  Reflection

Section 9 of 10

What worked

Designing the addressing before touching Packet Tracer paid off twice. Making every department a uniform /26 meant Change Request 1 was a cabling exercise rather than a redesign, and reserving the top half of the /16 meant the branch-office constraint cost nothing at HQ. Writing each device's configuration as a reviewable file first, applying one device at a time and checking with a show command before moving on, kept the build understandable: when something looked wrong, the list of things that could have changed was short.

What went wrong, and what it taught

Three mistakes were the most useful part of the project. First, the original core port plan assumed five Gigabit ports that a 2960-24TT does not have; the lesson was to check a plan against the real device before building, not after. Second, I first cabled the like-device links straight-through; Packet Tracer would have accepted them, but checking the work against the "correct cabling" criterion showed that "it works" and "it is right" are different standards. Third, and most important, during the fault demonstration I pasted the Warehouse switch's configuration onto the core switch. The symptom did not match my prediction, because the Admin control test failed too. The easy path was to record that as a result. Instead I treated the mismatch as a second, unknown problem, found the core switch's prompt reading SW-WH#, confirmed with CDP that it was physically the core switch, restored it, and re-ran the demonstration cleanly. The early failures were at first put down to spanning tree reconverging; that explanation was wrong, and it was corrected once the real cause was clear. That episode taught me more about troubleshooting than the planned fault did: a control test is only valuable if you are willing to believe it when it contradicts you.

What I learned about the assigned challenge

The VLAN-pruning fault is hard because nothing looks broken. The link is up, the switch ports are green, local traffic works, and the person reporting it will say "the Warehouse network is down". Scoping first (what works, what does not, and for whom) removed most of the network from suspicion before I ran a single diagnostic command, and one comparison, the allowed list on four ports side by side, found the cause. Writing the fault catalogue in Section 5.9 also showed me that several different faults produce nearly the same symptom, so the first check has to be the one that tells them apart, not the one that is easiest.

What I would do differently

  • Run show ip nat translations immediately after the NAT ping, and capture a standalone Warehouse inter-VLAN ping as its own test.
  • During the fault, also run show ip interface brief on R1 to show that R1's Warehouse subinterface is up and rule it out directly rather than by inference.
  • Add a hostname check, show running-config | include hostname, before pasting any configuration, so the wrong-device mistake is impossible rather than merely caught.
  • Add the security and redundancy features in Section 8, starting with inter-VLAN ACLs and a second DHCP path, since they would reduce the blast radius of exactly the kind of one-line mistake this project simulated.
